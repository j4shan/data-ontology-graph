# System design: functional

## Structure

| ID | Clause |
| --- | --- |
| 1.1 | The graph builder establishes validated memberships of dataset entity definitions in registered logical entities. Shared relationship inference derives a requested endpoint pair from those definitions; no component independently inserts, edits, or deletes a relationship. |
| 1.2 | The publisher builds and validates a complete candidate and owns replacement of the one current graph artifact at a caller-supplied path. |
| 1.3 | One OS-managed background graph service loads the current artifact and serves every local request. It keeps the snapshot, the static lexical trie, object maps, logical-entity membership indexes, a cross-entity relationship adjacency index, and sparse annotations in memory as service infrastructure, never as reasoning-session state. Loading does not enumerate the implied pairwise relationships between entity definitions or construct an adjacency or path-edge collection for all such pairs. |
| 1.4 | The `data-ontology-graph-launchd` command manages the service as an on-demand, user-owned `launchd` job whose property list lives in the service home, outside the directories `launchd` loads at login. `launchd` manages the process while the job is loaded; neither it nor the application manages a release history. |
| 1.15 | The `query-graph-api` skill in `skills/query-graph-api/` informs an agent that builds AKGs. It reaches graph knowledge only through the public JSON-RPC interface, using bundled standard-library scripts: the proxy `scripts/query.py` (2.6.4), the socket client `scripts/graph_call.py` that the other scripts share, and the service controller `scripts/service.py`, which starts, stops, and checks the on-demand service. The agent writes the AKG file itself. |

## Interfaces

### Local tool interface

| ID | Clause |
| --- | --- |
| 2.1.1 | The service exposes one JSON-RPC 2.0 request/response interface over a Unix-domain socket. Every call carries a request `id` and receives exactly one result or error. Notifications are not supported, and HTTP/OpenAPI is not part of the interface. |
| 2.1.2 | The methods are `graph.snapshot_info`, `graph.search`, `graph.get_dataset`, `graph.get_entity_definitions`, `graph.get_relationship`, `graph.get_entity_links`, `graph.get_dataset_edges`, and `graph.find_paths`. `graph.snapshot_info` reports the graph API version, the snapshot version, and the numbers of datasets, entity definitions, logical entities, and cross-entity relationships. |
| 2.1.3 | Responses are uncompressed text that the agent reads as sent. Response size is reduced by response structure, not transport compression. |
| 2.1.4 | Each operation returns a lightweight default and lets the caller request non-default metadata. Navigation methods do so through detail levels and added fields (2.4.6–2.4.8). |
| 2.1.5 | Every dataset, entity definition, relationship between entity definitions, and cross-entity relationship in a response carries `unknown_fields`, naming its typed claims whose value is `unknown`. A directed edge names unknown claims relative to the dataset it leaves (`multiplicity`, `match_existence`, `reverse_multiplicity`, `reverse_match_existence`); canonical detail for a relationship between entity definitions names them `a_to_b.*` and `b_to_a.*`. A cross-entity relationship names unknown claims relative to the requested logical entity or the direction of travel as `multiplicity`, `match_existence`, and `reverse_match_existence`. |
| 2.1.6 | `api_version`, currently `"6"`, names the graph API contract: its methods, parameters, and response shapes. It rises only on a breaking change, such as a renamed or removed method, parameter, or field, or a changed meaning. Additions keep the same API version. |

### Search

| ID | Clause |
| --- | --- |
| 2.2.1 | `graph.search` takes an optional `kind`, a non-empty list of `identity`, `dataset`, `entity_definition`, `entity_relationship`, and `column`. Omitting it searches all five. |
| 2.2.2 | Candidates may match a stable ID, business name, synonym, tag, description, qualified dataset name, accessor `kind`, `endpoint`, label key or value, key or string value of accessor `properties`, dataset-column set, column metadata, or entity metadata. A cross-entity relationship matches its descriptions. |
| 2.2.3 | The response has one group per requested kind, in the order `column`, `dataset`, `entity_definition`, `entity_relationship`, `identity`. Each group holds `subject_rows` read through `subject_row_header` and `match_rows` read through `match_row_header`, joined by `key`. |
| 2.2.4 | Subject rows are `column`: `key`, `node_id`, `column_name`; `dataset`: `key`, `qualified_name`, `unknown_fields`; `entity_definition`: `key`, `entity_expression`, `node_id`, `identity_id`, `dataset_columns`, `unknown_fields`; `entity_relationship`: `key`, `endpoints`; `identity`: `key`, `name`. A `dataset` key is its `node_id` and an `identity` key its logical entity ID; `column`, `entity_definition`, and `entity_relationship` keys are the object's ID (3.6.1). Match rows are `key`, `match_type`, `match_field`, `matched_term`, `matched_value`. |
| 2.2.5 | A subject has one match row per matching field value. `match_field` names the property holding `matched_value`, the original text, and `matched_term` is the normalized text that matched. Stored terms are the whole normalized value and each of its words. |
| 2.2.6 | `exact` means a stored term equals the normalized query, and `prefix` means a stored term starts with it. For a multi-word query against a word-match value, `phrase` means consecutive words of the value start with the query words in order, and `all_words` means each query word starts some word of the value. All query words must occur in the same value. |
| 2.2.7 | A value matching several ways reports only its best type, in the order `exact`, `prefix`, `phrase`, `all_words`. Values other than the word-match values match a multi-word query only when they start with the phrase. |
| 2.2.8 | Subjects are ordered by best match type, then normalized label, then key; a subject's match rows by match type, then field. The result limit applies to each group separately. A group's `truncated` is true when the limit omits eligible subjects, and the response's `truncated` is true when any group's is. |

### Navigation

| ID | Clause |
| --- | --- |
| 2.3.1 | Dataset navigation methods use the logical-entity membership index as their source of relationship evidence. Neighbour listing derives requested endpoint pairs and presents their outgoing directed edges; a relationship whose endpoints lie on the same dataset gives two directed edges. Path search (2.3.6, 2.3.7) derives entity links between logical entities from the same memberships and the cross-entity relationship adjacency index. Internal derivation preserves the existing public traversal semantics, filters, ordering, bounds, and response shapes. Entity link listing (2.3.12) derives entity links as path search does. |
| 2.3.2 | A dataset that lists adjacency in a `get_dataset_edges` response lists its directed edges in edge groups, one per logical entity ID in ascending order, each holding that dataset's definitions in ascending `dataset_columns` order. Directed edges within a definition are ordered by target node ID and target columns. `edge_count` counts the directed edges eligible under the operation's filters, and `truncated` means this response omits some of them. `get_dataset_edges` (2.3.10), `get_entity_links` (2.3.12), and `find_paths` (2.3.6) page their results. A definition with no eligible directed edges has no entry. |
| 2.3.3 | `graph.get_dataset_edges` takes `node_id`, `limit` (default 200 per definition per page, range 1–1000), optional source `identity_id` and `from_dataset_columns`, optional `target_identity_ids` (default `[]`, deduplicated and sorted, AND semantics), `view` (`auto`, `aggregated`, or `detailed`, default `auto`), `fan_out_threshold` (default 200, range 1–10,000), optional `cursor`, and the shared navigation presentation options. A source filter matching no definition is invalid params; an unknown target logical entity is resource not found. A registered target with no matching neighbours gives an empty selection. `auto` returns an aggregated view only when filtered fan-out exceeds the threshold; an explicit view overrides the automatic choice. A cursor continues detailed results, including with `view="auto"`; an aggregated request cannot carry a cursor. Every response reports `snapshot`, the actual `view`, `node_id`, `limit`, source filters, canonical target filters, `fan_out_count`, and `fan_out_threshold`. |
| 2.3.5 | `graph.get_entity_definitions` discovers entity definitions through dataset memberships without enumerating relationship pairs. A required primary `identity_id`, optional primary `entity_universe` filter, and up to four distinct additional `target_identity_ids` select datasets using AND semantics. Filtering precedes exact dataset and qualifying-primary-definition counts. `auto` aggregates above `dataset_threshold` (default 200); callers may explicitly select either view. Aggregation reports the top 20 other logical entities by definition count and identity ID, including distinct-dataset counts and histogram omissions. Detailed results page whole datasets by node ID, defaulting to 100 and allowing at most 1,000 per page, with qualifying primary definitions and definitions of selected targets. Stateless cursors bind snapshot content, API version, method, filters, bounds, and response format. Auto continues detailed pages; null `next_cursor` ends enumeration. Detailed `truncated` reports omissions from the current page, including earlier pages. Both views support table and records formats. The operation uses bounded worker concurrency and cooperative cancellation. |
| 2.3.6 | `graph.find_paths` takes logical entity IDs `source_identity_id` and `target_identity_id` (equal IDs ask for a self relationship), `max_links` (default 2, range 1–6, bounding the whole path or, with participants, each whole leg), `link_kinds` (`all`, the default, or `stated`), optional `multiplicity` and `match_existence` lists read in the direction of travel, `order` (`any`, the default, or `converging`: `many:1` links, then `1:many` links, `1:1` fitting either), `avoid_identity_ids`, up to 3 `participant_identity_ids` with `participation` (`legs`, the default, with `shape` `both`, `independent` or `shared_chain`; or `closed`, with `k_unnamed` 0–2), `exclude_restatements` (default true), `self_links` (default false: a logical entity may take one self link inside a path), `limit` (default 50, range 1–200), and `cursor`. Closed participation requires participants and takes no `multiplicity`, `match_existence` or `order`; participants and avoided logical entities exclude the source, the target and each other. It returns `total`, `total_is_lower_bound`, `tie_group_count`, the ranked page `results`, `filter_report`, `relaxations`, `leg_counts` for legs, and `next_cursor`. A result has `rank`, `tie_group`, `shape` (`path`, `shared_chain`, `independent`, or `closed`), `entities` (`identity_id`, `name`, `dataset_count`; in path order for a path and in ID order for a subgraph), `links`, and `legs` or `unnamed_identity_ids`. A link has `from_identity_id`, `to_identity_id`, the `multiplicities` and `match_existences` derived on its common datasets (product/graph-model.md 3.16, 3.17), `common_dataset_count`, and `stated`, the stated cross-entity relationship's `id`, descriptions, `multiplicity`, `match_existence`, `reverse_match_existence` and `unknown_fields` read from `from_identity_id`, or null. `filter_report` gives, under the same bound, link kinds, avoided logical entities and self links with the claim filters removed, `unfiltered_total`, `by_links`, `fewer_links_total`, `unknown_multiplicity_total` (paths with a link whose multiplicity is unknown on every pivot), `to_one_total` (every link `many:1` or `1:1`), `from_one_total` (every link `1:many` or `1:1`), `converging_total`, each count's lower-bound flag, up to 10 `through_entities` with their path counts, and for legs `leg_counts` per participant. `relaxations` lists, on every response, each single request `change` whose result is larger than `total`, with its `total` and `total_is_lower_bound`: wider claim filters (the converging order, then any multiplicity), no match-existence filter, each avoided logical entity allowed, all link kinds, closed participation with 0 or 1 unnamed logical entities for legs, one more unnamed logical entity or legs for closed participation, self links, restatements kept, and one more link. An unknown logical entity is resource not found. |
| 2.3.7 | Path search derives entity links on demand and caches them per snapshot: a logical entity's definitions give its datasets, whose definitions give the linked logical entities after one deduplication; a dataset holding two definitions of one logical entity gives a self link; the cross-entity relationship adjacency index adds stated links. Each way to make an entity link is a pivot: one definition of each logical entity on a common dataset, or the stated relationship with its claims. A link is usable when it is stated (with `link_kinds` `stated`) and some pivot passes the claim filters in the direction of travel. A breadth-first pass from the target over usable links gives distances, and a depth-first enumeration of simple paths expands only logical entities whose distance fits the bound, checking cancellation at each expansion; with `self_links`, a logical entity may also link to itself once before moving on. A path is kept when one pivot per link passes every claim filter and the order and, with `exclude_restatements`, no two consecutive dataset pivots share one definition of the middle logical entity; a stated pivot never restates. Legs are the kept paths containing a participant: `shared_chain` results contain every participant, and `independent` results combine the 10 shortest legs per participant that avoid the other participants. Closed results try each set of up to `k_unnamed` logical entities linked to two or more named ones and keep a set whose induced links put every participant and unnamed logical entity on a source-to-target path, with links read away from the source. Paths rank by links, legs by distinct links, closed results by unnamed count then links; then by the links whose multiplicity is unknown on every pivot, the shape and the logical entity IDs. Equal keys share a tie group. The filter report repeats the enumeration with the claim filters removed and with the to-one, from-one and converging filters, and the search is rerun with each single relaxation. An enumeration stops at 20,000 paths, a relaxation count at 1,000, or on cancellation, and its counts are then lower bounds. The cursor encodes the offset within the request's scope. |
| 2.3.8 | `graph.get_relationship` takes an `edge_id` and optionally the endpoint to read it from, as `from_node_id` and `from_dataset_columns`. `from_dataset_columns` is required when both endpoints lie on `from_node_id`. It always returns canonical `endpoint_a`, `endpoint_b`, `a_to_b`, and `b_to_a`, with the endpoint datasets as `standard` dataset records (2.4.4) and their entity definitions alongside. With an endpoint, it also returns the directed edge leaving that endpoint as one array in `edge`, at `standard` positions named by `edge_fields`; without one, both are null. The directed edge is a view and never changes the stored relationship. |

| 2.3.10 | A detailed get_dataset_edges response adds `Navigation` and `next_cursor` to its selection context. The source dataset is at distance 0, and other targets of listed edges are at distance 1 and list no adjacency. `limit` applies independently to each source definition on each page. Group counts cover all eligible directed edges in the full filtered selection; top-level `truncated` means the current page omits some of that selection, including edges on previous pages. `next_cursor` is null exactly when no further page exists. Continuation is stateless and bound to a fingerprint of the complete snapshot, the API version, source and target filters, page limit, threshold, detail, added fields, and response format. Resubmitting the same request with the cursor may change only `view` between auto and detailed. Malformed, mismatched, stale, or out-of-range cursors are invalid params. |
| 2.3.11 | An aggregated get_dataset_edges response echoes `detail` and `fields` and contains `histogram`, `logical_entity_count`, and `truncated`, with no detailed dataset or directed-edge collections. Histogram columns are `identity_id`, `name`, `entity_definition_count`, and `dataset_count`. It lists at most 20 logical entities by descending definition count then ascending identity ID. `logical_entity_count` counts all histogram groups before the top-20 cut; `truncated` indicates omitted groups. Fan-out and histogram inputs are all distinct connected datasets passing the source and target filters, excluding the source dataset. Each target definition contributes once, repeated roles count separately, and each target dataset contributes once to its entity's dataset count. Aggregates are computed before any detailed page bound. Detailed results preserve same-dataset relationships when their target dataset meets the filters. |
| 2.3.12 | `graph.get_entity_links` takes a required logical entity `identity_id`, `link_kinds` (`all`, the default, or `stated`), optional `multiplicity` and `match_existence` lists read from the requested logical entity, `avoid_identity_ids` (not `identity_id`), `limit` (default 200, range 1–1000), and an optional `cursor`. It returns `identity_id`, `name`, `limit`, `link_count`, `links`, `truncated`, and `next_cursor`. `links` lists the entity links from the requested logical entity that pass the filters, ordered by the other logical entity's ID. A link passes a claim filter when one pivot (2.3.7) passes it. Each link has the other logical entity's `identity_id`, `name`, and `dataset_count`; the `multiplicities` and `match_existences` derived on its common datasets, read from the requested logical entity (product/graph-model.md 3.16, 3.17); `common_dataset_count`; and `stated`. `stated` holds the stated cross-entity relationship's `id`, descriptions, `multiplicity`, `match_existence`, `reverse_match_existence`, and `unknown_fields` read from the requested logical entity, or is null. A self link, from two definitions of the logical entity on one dataset or from a stated self pair, appears once. `link_count` counts every link passing the filters, `truncated` reports whether the page omits any, and `next_cursor` is null when no further page exists. The method takes no detail level. An unknown logical entity is resource not found. |

### Graph-object responses

| ID | Clause |
| --- | --- |
| 2.4.1 | Detailed navigation responses and `graph.get_relationship` write a directed edge as one array without field names, with an `edge_fields` header naming its positions. Position `edge` is `"<start node_id>[<columns>] -> <end node_id>[<columns>]"`, with columns in `dataset_columns` order; node IDs and column names containing `,`, `[`, `]`, `"`, or `->` are JSON-quoted. Then come `multiplicity` and `match_existence`; from `standard` detail, reverse claims and effective endpoint descriptions; at `full`, `annotation`; and `edge_id` last. Inside an edge group, its logical entity ID is carried by the group; callers may add `identity_id` through `fields`, and it follows `edge`. Aggregated `get_dataset_edges` responses contain a histogram instead of directed edges or dataset collections. |
| 2.4.2 | An edge group is `{identity_id, entity_definitions}`, and each entry of `entity_definitions` is `{id, dataset_columns, edge_count, truncated, edges}`. In `"records"` format, each dataset record that lists adjacency nests its edge groups under `edge_groups`, so a dataset's adjacency reads in one record, and navigation responses carry no separate relationship list. A relationship whose endpoints are both returned appears as one directed edge in each endpoint's dataset. In both formats, edge groups and directed-edge arrays are the same, and the formats differ only in dataset fields. |
| 2.4.3 | In `"table"` format, a collection is `{"header": [...], "rows": [[...]]}` and dotted column names identify record paths. Detailed navigation splits datasets, columns, and definitions into their keyed collections and lists edge groups with `node_id`; records nest those objects on datasets. Aggregated `get_dataset_edges` renders `histogram` as a table or an array of records according to `response_format`. Any other format is invalid params. |
| 2.4.4 | Every response presents a dataset as one record: `node_id`, `qualified_name`, `accessor` (`kind`, `endpoint`, `labels`, `properties`), `grain`, `descriptor` (`display_name`, `description`, `synonyms`, `tags`), `unknown_fields`, `columns`, and `entity_definitions`, each present as the detail level selects (2.4.6). Absent `labels` is `{}`, and absent `properties` is `null`. Navigation responses add `distance` and `edge_count`, the number of directed edges leaving the dataset in the graph, whether or not they are listed, so an agent sees how much lies beyond the response. `graph.get_dataset` returns every field; the detailed `datasets` collections of `graph.get_entity_definitions` and `graph.get_relationship` use `standard` detail. |
| 2.4.5 | `graph.get_relationship` returns the canonical relationship record with `edge_id`, `identity_id`, `endpoint_a.node_id`, `endpoint_a.dataset_columns`, `endpoint_b.node_id`, `endpoint_b.dataset_columns`, `a_to_b.multiplicity`, `a_to_b.match_existence`, `b_to_a.multiplicity`, `b_to_a.match_existence`, `unknown_fields`, and `annotation`. |
| 2.4.6 | Dataset navigation methods accept `detail`: `essential`, `standard` (the default), or `full`. `essential`, for initial exploration, gives datasets `node_id`, `qualified_name`, `accessor.kind`, `distance`, and `edge_count`, and directed edges `edge`, `multiplicity`, `match_existence`, and `edge_id`. `standard` adds dataset `accessor.endpoint`, `accessor.labels`, `grain`, `descriptor.description`, and `unknown_fields`, and the `standard` directed-edge positions of 2.4.1. `full`, for validation, adds `descriptor.display_name`, `descriptor.synonyms`, `descriptor.tags`, `accessor.properties`, the dataset's `columns` and `entity_definitions`, and each directed edge's `annotation`. |
| 2.4.7 | Dataset navigation methods accept `fields`, a map from `dataset`, `edge`, or `entity_definition` to field names added to the chosen detail level. Unknown objects or fields are invalid params. Basic fields remain present in detailed results: a dataset node ID and qualified name, and an edge label and ID. Responses echo the resolved `detail` and added `fields`; detailed navigation also supplies `edge_fields`. Aggregated `get_dataset_edges` validates and echoes presentation choices but returns its fixed histogram columns. The bundled skill publishes the field catalog. |
| 2.4.8 | Dataset navigation detail levels do not change result bounds or the selected get_dataset_edges view. Default bounds are: get_dataset_edges 200 edges per source definition per detailed page, with automatic aggregation above 200 distinct connected datasets and a top-20 histogram; get_entity_links 200 entity links per page; find_paths 50 results of at most 2 entity links. Explicit request bounds override defaults within each method's maximum. |
| 2.4.9 | The `entity_definitions` collection, at `full` detail or when requested, has `id`, `node_id`, `identity_id`, `dataset_columns`, `entity_universe`, `unique`, `total`, `conforms`, `entity_expression`, `entity_metadata`, `description`, `effective_description`, `description_source`, and `unknown_fields`. `effective_description` is the definition's own `description` (`description_source` `entity`), else the description of its single column when every `entity_expression` is that bare or bracket-, quote-, or backtick-wrapped column (`column`), else null; it serves `product/graph-model.md#1.9`. A definition with an empty `entity_expression` identifies its logical entity by the combination of its `dataset_columns` (`product/graph-model.md#1.6`). The `columns` collection has `id`, `node_id`, `name`, `description`, `value_description`, and `synonyms`. |

### AKG contract

| ID | Clause |
| --- | --- |
| 2.6.1 | The public AKG contract is the JSON Schema `resources/schema/akg.schema.json` with a copy of the schema and a format guide bundled in the `query-graph-api` skill (`product/graph-api-skill.md#1.2`). One JSON document holds one objective: `status` (`draft` or `final`), `question`, an optional `objective` and graph snapshot, `edge_fields`, `datasets`, and optional `comparisons` and `gaps` keyed by agent-chosen IDs. The optional `graph.snapshot` records `api_version` and `version` from `graph.snapshot_info`. The AKG has no format version; its schema follows the graph API version. An AKG object takes the shape of the response it was concluded from. `datasets` is a list of dataset records (2.4.4) without the fields that describe only a response (`distance`, `edge_count`, and an entity definition's `edge_count` and `truncated`), holding only the selected columns. A dataset's selected directed edges sit in its `edge_groups` as in navigation responses (2.4.2), in the dataset traversal starts from, as directed-edge arrays at the `standard` positions the document's `edge_fields` names. Gaps name directed edges as (`definition_id`, `edge_id`), with `definition_id` the `id` of the entity definition the edge leaves. Connected components derive from the directed edges. Agent reasoning lives only in `usage` on a dataset and on an edge group's entity definition, where it is keyed by `edge_id` and holds `keep`, `aggregate_before_join`, and `note`, and in `comparisons` and `gaps`. Unknown keys are allowed anywhere. The schema is self-contained and is generated from a lenient model. |
| 2.6.3 | `data-ontology-graph-akg check FILE` reports findings by location, rule, and severity (`error`, `warning`, or `info`) and never refuses to load a parseable document. With `--socket PATH` or `--yaml PATH`, it also resolves every dataset field against `graph.get_dataset` and every directed edge, position by position, against `graph.get_relationship` read from the dataset that holds it. YAML resolution serves the YAML intermediary through the same read service, so both sources answer in one shape. It reports each mismatch by element and field. When the AKG records `graph.snapshot`, socket resolution reports a different `api_version` or `version` as a mismatch; YAML resolution, which rebuilds the snapshot, compares only `api_version`. `finalize` requires no error, treats dangling references as errors, requires that resolution, and then sets `status` to `final`. `export --format markdown` writes a deterministic, read-only copy for human review and shows `Snapshot: <version> (API <api_version>)` when a snapshot is recorded. |
| 2.6.4 | `scripts/query.py METHOD [PARAMS] --context PATH` sends one JSON-RPC request and prints the `result` or `error` member as returned. The context file (File A, `product/graph-api-skill.md#3.1`) is JSON holding `question` and `logical_entities`; the first call creates it from `--question`, each `--entity` adds a name once, and a different question is refused. The traversal file (File B) sits beside it with the suffix `.traversals.md` and receives one section per `get_dataset_edges` or `find_paths` call, including service errors: a heading naming the method and a Python literal holding the request and response as JSON strings. Other methods are printed only. Invalid local input makes no call and exits 2; a service or connection error exits 1, and a connection failure is not recorded. |

## Data

### Intermediary

| ID | Clause |
| --- | --- |
| 3.1.1 | The intermediary uses schema version `"1"`. Source-controlled JSON Schemas under `resources/schema/` govern the directory manifest (`intermediary-directory.schema.json`) and the assembled intermediary (`intermediary.schema.json`). |
| 3.1.2 | A finalized directory has a fixed `directory-manifest.yaml` beside its `yaml/` directory. The manifest names, relative to `yaml/`, exactly one logical-entity file and one or more node files. Its optional `entity_relationships` path names exactly one cross-entity relationship collection file; absence means there are no cross-entity relationships. Relationships between entity definitions are derived and have no source collection. |
| 3.1.3 | The manifest and every collection file declare schema version `"1"`; each collection file contains exactly its manifest-owned collection. Node files partition the assembled node list; logical entities and cross-entity relationships are not partitioned. The assembled intermediary has an optional `entity_relationships` list; each item has `endpoints` (two logical entity IDs), required `multiplicity` (one value read from the first endpoint to the second), required `match_existence` (two values in endpoint order), and `descriptions`. |
| 3.1.4 | Manifest paths are relative, stay within the YAML directory after resolution, and name existing `.yaml` or `.yml` files. Absolute paths, parent traversal, symlink escapes, duplicate paths, missing files, and unlisted files are rejected. |
| 3.1.5 | A finalized YAML directory contains only manifest-listed collection files. The manifest sits beside it, not inside it. |
| 3.1.6 | `dataset_columns` is a non-empty, duplicate-free list in ascending exact-name order, and every member exists in the node's column inventory. |
| 3.1.7 | A grain component that names an `identity_id` resolves to an entity definition with the same column set on that node. |
| 3.1.8 | `node_id` is a stable string chosen by the contributor and unique in the graph; it does not depend on accessor content. The intermediary schema states this rule. SQLite qualified names are `<catalog>.<schema>.<table>`. |
| 3.1.9 | For each cross-entity relationship, the build requires both `endpoints` to resolve to registered logical entities and to appear in ascending lexical order. It rejects a repeated endpoint pair, an empty `descriptions` list, a blank description, or duplicate descriptions within one list. It requires one `multiplicity` value from `1:1`, `1:many`, `many:1`, `many:many`, and `unknown`, and exactly two `match_existence` values from `always`, `optional`, and `unknown`, in endpoint order. A contributor must state `unknown` explicitly. Each deterministic violation is reported with its location and is never auto-resolved. |

### Accessors

| ID | Clause |
| --- | --- |
| 3.2.1 | An accessor holds non-blank `kind` and `endpoint` strings, optional `labels` mapping non-empty keys to strings, and an optional non-empty `properties` object of any JSON values (`product/graph-model.md#2.6`). The snapshot stores and serves it as written. |
| 3.2.2 | The build rejects two datasets whose accessors have equal `kind`, `endpoint`, and canonical-JSON `properties`; `labels` are not compared (`product/graph-model.md#2.7`). The build report warns about each accessor whose canonical JSON serialization, omitting absent optional fields, exceeds 256 characters, and the build continues (`product/graph-model.md#2.8`). |

### Relationships

| ID | Clause |
| --- | --- |
| 3.3.1 | A relationship's `edge_id` is `D<i>-D<j>`, the IDs of `endpoint_a` and `endpoint_b` with `i < j`. `endpoint_a` precedes `endpoint_b` in ascending lexical order of `node_id`, `identity_id`, and `dataset_columns`, which is ascending ordinal order; presenting the reversed pair swaps its `a_to_b` and `b_to_a` claims. The inferrer resolves an `edge_id` by ordinal and requires two distinct definitions of the same logical entity in canonical order; any other `edge_id` names no relationship. Resolution stores no relationship pairs. |
| 3.3.2 | A concrete relationship contains its endpoint references and derived relationship properties only. Entity expressions, expression context, accessor information, and other node metadata stay on the connected nodes. Relationship-specific annotations are stored sparsely under the canonical pair identity; they do not require a stored record for every possible pair. |

### Snapshot

| ID | Clause |
| --- | --- |
| 3.4.1 | A snapshot carries its `version`, the UTC build time to the second in `YYYY-MM-DDTHH:MM:SSZ` form, its logical entities (`logical_identities`), dataset nodes with their entity definitions, `entity_relationships`, and sparse annotations. The entity definitions are the authoritative logical-entity memberships. An artifact does not persist an array of all derived relationships between entity definitions. |
| 3.4.2 | A snapshot rejects duplicate node or logical-entity IDs, invalid or duplicate entity definitions, and references to unknown nodes, logical entities, or definitions. It validates cross-entity relationship endpoints, ordering, pair uniqueness, and descriptions by the rules in 3.1.9. An annotated relationship must resolve to two distinct definitions of the same registered logical entity. Validating a membership snapshot does not enumerate unannotated endpoint pairs. |
| 3.4.3 | The registry and dataset definitions are persisted in `nodes.json`, sparse annotations in `annotations.json`, and cross-entity relationships in `entity_relationships.json`, with matching snapshot versions. An artifact without `entity_relationships.json` has no cross-entity relationships. Loading rebuilds membership indexes without reading an all-pairs edge file. |
| 3.4.4 | Loading builds one in-memory adjacency index from each logical entity to each related logical entity and their cross-entity relationship. Each cross-entity relationship is referenced under both endpoints, or once when both endpoints are the same logical entity. This index does not alter membership-derived relationships between entity definitions. |

### Search index

| ID | Clause |
| --- | --- |
| 3.5.1 | The search index is a static `marisa-trie` `RecordTrie` of mechanically normalized terms. Posting records reference authoritative snapshot objects rather than duplicating them; several terms, including synonyms, may reference one object, and one term may reference several objects. |

### Identifiers

| ID | Clause |
| --- | --- |
| 3.6.1 | Contributor-authored IDs, `node_id` and the logical entity ID `identity_id`, are opaque: the system compares them and never parses them. Each entity definition, column, and cross-entity relationship has a snapshot-local ID: `D`, `C`, or `X` followed by its decimal ordinal from 1 without leading zeros, assigned in ascending order of its natural key, `(node_id, identity_id, dataset_columns)`, `(node_id, column name)`, or the ascending pair of logical entity IDs. Identical content yields identical IDs; any content change may renumber them. A relationship between entity definitions is not stored, and its `edge_id` composes its endpoints' IDs (3.3.1). Requests name objects by authored IDs and natural-key fields, and a relationship by `edge_id`. |
| 3.6.2 | A snapshot-local ID is valid only in the snapshot that assigned it. Every response carries `snapshot` with `api_version` and `version`; a caller holding IDs detects a different snapshot by its `version` and handles it, and the service does not detect IDs from another snapshot. Callers compare IDs and never parse them. Wherever an order uses IDs, it compares ordinals numerically, which matches natural-key order. |

## Flows

| ID | Clause |
| --- | --- |
| 4.1 | For directory input, the build validates the sibling manifest, path containment, file inventory, collection ownership, and schema-version agreement; assembles the collections; and validates the result against the intermediary schema. Single-file input is validated directly as an assembled intermediary. |
| 4.2 | After the schema gate, construction validates node and logical-entity references, canonical column sets, entity-definition uniqueness, the required `unique`, `total`, and `conforms` properties, the descriptor, accessor fields and duplicate-accessor check, grain or explicit unknown grain, column inventory, definition-scoped `entity_universe`, and cross-entity relationships with their required claims (3.1.9). It indexes each definition under its registered logical entity and writes those memberships without enumerating endpoint pairs. The multiplicity and match existence of a relationship between entity definitions are derived when a pair is requested (`product/graph-model.md#3.2`, `#3.3`); those of a cross-entity relationship are read as stated (`#3.14`, `#3.15`). The build report counts entity definitions and cross-entity relationships and locates unknown input claims, including unknown cross-entity relationship claims, by stable IDs without listing every implicit relationship. |
| 4.3 | Publication builds and reload-validates a complete candidate, replaces the current-artifact directory as one unit, restores the prior artifact if promotion fails, and removes its transient backup after success. When the replaced directory holds files that are not artifact files, publication removes them and reports each one as a warning. |
| 4.4 | After a publication, the maintainer reloads the in-memory service against the stable artifact path. |
| 4.5 | The lifecycle command resolves the artifact path, verifies the artifact exists and loads, writes the `launchd` property list into the service home at `setup`, and at `start`, `stop`, and `reload` invokes only the `launchctl` operation the job's loaded state requires, then calls `graph.snapshot_info` to verify the running service. It never searches for a newest artifact, compares versions or timestamps, follows a `latest` pointer, or validates a release manifest. |
| 4.6 | The intended agent interaction is progressive: discover candidate entities, inspect selected entities, and retrieve relationship evidence through lookup or navigation. |
